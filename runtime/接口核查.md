## 2026-11-27 复核

下载目录中的 ssloader v1.0.1 压缩包包含 winmm.dll 和 README-ssloader.txt。说明确认它在游戏启动时加载 ssmods 目录中的 DLL。说明未列出图形菜单或模型刷新 API。

在 SHA256 为 69DDB71FB6768A097F9BFF204201F3A9CE960F1A325F5ED3A5C9160DC64A6AE8 的原版程序中，图形菜单标题、全屏、垂直同步、分辨率和图形质量的本地化键均由同一设置界面函数引用。全屏和垂直同步会分别按当前状态选取开关文案，以相同的描述结构调用同一例程。两项传入的行标识分别为 0 和 1。此处是菜单行构建的静态证据；选择事件的处理和运行时外观更新仍待验证。

### 角色名称与外观切换

原版程序 RVA 0x219A20 接收长度和字符串指针，按长度分支后比较角色名，返回角色编号。可找到 11 处直接调用。其中 RVA 0x323333 所在的逻辑按角色处理剧情对话，同处可见水手和测量员对话键。修改这个分类结果会影响玩法判断。外观切换应保留实体原有的角色编号，在显示资源的选择处区分两套模型。当前尚未验证该显示入口。

### 模型绑定与职业编号的交叉检查

在原版程序 69ddb71f… 的 REA/Ghidra 函数报告中，RVA 0x195C60 先读取实体 +0x108 选择动画存储位置，再从实体 +0x88 所指对象的前两个机器字读取默认名字。第三参数提供非空名字时，查找使用传入的名字。此行为仅证明动画查找支持单独指定名字，不能据此推断绘制网格也会改变。

调用侧 RVA 0x28436E 将对象指针写入实体 +0x88。另一路径 RVA 0x2861BF 从实体 +0x88 读取指针并传给名称分类函数 RVA 0x219A20。因而覆盖该实体字段会同时改变职业分类的输入。heroes1_9 的单字段对照也出现相应现象：传送法师换成商人外形后仍能与水晶换位，但头顶数字由 3 变成 9。

后续验证应保持分类所读取的逻辑名称，单独追踪网格提交和动画查找。通过标准包括同一法师保留编号 3、显示替代模型、完成与水晶交换及撤销。

### ssloader v1.0.1 的插件入口

核对随包 README 和 winmm.dll 的插件枚举循环后，确认该版本对每个插件调用 LoadLibraryExW，随后检查返回值、写入 ssloader.log 并遍历下一项。该循环没有按导出名调用初始化函数。加载器使用 GetProcAddress 的系统 winmm 转发路径和插件枚举路径是两个独立分支。

因此，安装日志中的 loaded (0) 仅证明 Windows 成功加载了该 DLL。RedPandaMenuRow、RedPandaConfirmMenuRow 和 RedPandaApplyScene 都需要显式的调用方。发布验收应在通过安装器部署的副本中正常启动游戏，仅用游戏菜单完成两次切换并记录画面。此前通过 QA 辅助程序调用的结果保留为组件验证。
